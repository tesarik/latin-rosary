# latin-rosary

A single-page web app for praying the Latin rosary and other Latin prayers (the *Orationes utilissimæ*, seven litanies, the Leonine and St. Bridget prayers, user-defined plans). UI chrome and menus are in Czech ("Latinský růženec") or English; all prayer texts are in ecclesiastical Latin, with a Czech or English translation one tap away. Source of truth for the prayer texts is `Posvátný růženec latinsko – česky.pdf` (not in repo).

## Stack

- **React 18** + **Vite 6**, **TypeScript** in strict mode (`tsconfig.app.json` for app code, `tsconfig.node.json` for `vite.config.ts`, root `tsconfig.json` references both).
- No CSS framework — all styling is inline `style={{...}}` objects in the React tree. The one stylesheet, `src/index.css`, holds the box-model reset **and the light/dark theme tokens** (CSS custom properties); inline styles reference neutrals as `var(--…)` so the palette flips by toggling `data-theme` on `<html>`. See **Theming** below.
- No router, no state library. Vitest covers the pure logic (`*.test.ts`, no DOM). `Rosary.tsx` orchestrates a handful of small components in `src/rosary/`.
- PWA: `public/manifest.webmanifest` + `public/sw.js` (network-first for navigations, cache-first for assets) + `public/icon.svg`. The SW cache name is `ruzenec-__SW_VERSION__` and the `swVersion()` plugin in `vite.config.ts` rewrites the placeholder at build time to `ruzenec-<pkg.version>-<base36-timestamp>` so each production build gets its own cache bucket and the `activate` handler drops every other `ruzenec-*` bucket (only its own prefix: other apps on the same domain share the Cache Storage). The SW does **not** `skipWaiting()` on its own — a new build waits until the user accepts the in-app "update available" prompt (`useServiceWorkerUpdate` → `UpdateToast`), which posts `SKIP_WAITING`; a one-time `controllerchange` reload then swaps in the fresh assets.
- Deploys as a static site. Sub-path is configurable via `BASE_PATH` env var (read in `vite.config.ts`); the manifest, icon links, and SW registration scope all flow from `import.meta.env.BASE_URL`.

## File map

- `src/main.tsx` — entry; mounts `<Rosary />` inside `<ErrorBoundary>`. Imports the EB Garamond faces and preloads their Latin Extended subset (see Typography). Service-worker registration now lives in `useServiceWorkerUpdate` (used by `Rosary`), not here.
- `src/Rosary.tsx` — **orchestrator**: state (`selectedSet`, `currentStep`, `sequence`, `started`, and the per-set `progress` map), `next` / `prev` / `jumpTo` / `exitToMenu` / `finish` / `confirmRestart`, persistence wiring, wake-lock effect, keyboard + swipe handlers, header + progress bar + bottom-nav layout. The header has **two rows**: the controls on top — back `←` and restart `↺` on the left; theme, text size "Aa" and the 🌐 language button (far right) on the right — and the set's name across the full width below, so a long litany name never squeezes between buttons. For every set the progress — the rosary's bead ring (height capped at `30dvh` so it fits small phones) or a linear set's bead strand — and the label chip are pinned above a **contained** `PrayerCard` (`contained` + `scrollRef`): the card sits right under the label (not centred, so it doesn't jump as text length changes), grows with its text up to the navigation, and then scrolls its text *inside*, so neither the progress nor the card's rounded top and shadow ever scroll away. In the contained card only side padding sits on the scroller (vertical padding is inside it), because a sticky ℟ band sticks at the scroller's padding edge. Set-key classification, sequence building, persistability, initial-state resolution, and the step-bounds check are delegated to `rosary/navigation.ts` (pure, unit-tested). Renders `<MysteryMenu>`, `<PlansScreen>` (when the plans tile is open) or the prayer screen, plus the `<UpdateToast>` when a SW update is ready. Also owns the plan list (`loadPlans` at mount, `savePlans` on change) and the one-shot import of a plan shared via the `#plan=…` URL fragment, and opens a prayer set named by a `#pray=<key>` fragment (the static prayer pages' *Pray it in the app* link). A prayer set has one of three `kind`s: `rosary` (bead ring + progress bar), `linear` (section bead-strand stepper), or `single` (one standalone prayer — no bead ring/section stepper and no progress bar, just the label chip + prayer card).
- `src/rosary/navigation.ts` — **pure session/navigation logic** extracted from the orchestrator (no React/DOM): `PrayerSetKey`/`PrayerSetKind` types, the `isRosaryKey`/`isChapletKey`/`isOrdinaryKey`/`isLitanyKey` guards, `getPrayerSetMeta`, `buildSequence`, `isPersistableKey`, `resolveSession(saved)` (validates the open set and every progress entry), `resumeStep(key, step)`, and `canGoToStep(idx, current, length)`. User plans aren't a static registry, so the four functions that can meet a `plan:<id>` key take the live `Plan[]` as a second argument instead of reaching for storage themselves. Registry membership uses an **own-property** check (`hasOwnProperty`), not `in`, so a corrupt saved key like `"toString"` can't resolve to a prototype member. Covered by `navigation.test.ts`.
- `src/rosary/ErrorBoundary.tsx` — top-level error boundary (class component). Catches an uncaught render error and shows a themed, localized recovery card: **Reload**, or **clear saved progress and reload** (`clearSavedState()`) for the likely corrupt-`localStorage` case. Reads the persisted locale directly (no React context).
- `src/rosary/useServiceWorkerUpdate.ts` — PWA update hook (production only): registers the SW, detects a waiting new build, and returns `{ updateReady, applyUpdate, dismissUpdate }`. `applyUpdate` posts `SKIP_WAITING`; a `controllerchange` reload swaps in the new assets (guarded so the first-ever install doesn't spuriously reload).
- `src/rosary/UpdateToast.tsx` — bottom "a new version is available" prompt (themed, localized) rendered by `Rosary` while `updateReady`; Update applies the waiting SW, × dismisses.
- `src/rosary/prayers.ts` — `PRAYER_TYPES`, `MYSTERIES`, `PRAYERS` (the Latin texts), the per-locale translations `PRAYERS_CS` / `PRAYERS_EN` behind `PRAYER_TRANSLATIONS`, `getHailMary(mystery)` / `getHailMaryTr(locale, mystery)`, and the exported types `Localized`, `MysteryKey`, `MysterySet`, `PrayerType`, `StaticPrayerType`, `HailMary`. Anything shown in the user's language is a `Localized` (`Record<Locale, string>`) — display names (`nameTr`) and the mystery clauses (`mysteriesTr`) — never a `…Cs`-suffixed field.
- `src/rosary/sequence.ts` — `buildRosarySequence(mysterySet)` and the `SequenceItem` type (stamps each bead-bearing item with a `beadId`); the `OTHER_PRAYER_SETS` registry of multi-step linear sets (Leonine, St. Bridget, and St. Joseph's seven sorrows and joys — `ioseph`, the **short Latin form**: seven `IOSEPH_*` headings in red rubric over their Pater Noster (the `ioseph()` helper in `prayers.ts`), each followed by an unsectioned Ave María and Glória Patri as St. Bridget's are, then *Vírginum custos* — 22 steps; the long Raccolta prayers have no Latin; and `defuncti`, *Preces pro defunctis*: Pater Noster, Ave María, then `DE_PROFUNDIS` cut by `lines` into psalm, versicles and collect, five sectioned steps) with their builders; the `ORDINARY_PRAYERS` registry (`OrdinaryPrayerKey`) of standalone single prayers — the *Orationes utilissimæ* prayers (Signum Crucis, Pater Noster, Ave María, Gloria Patri, both Creeds + Symbolum Athanasiánum, the four seasonal Marian antiphons, Sub tuum præsídium, Angelus Dómini, Ánima Christi, Angele Dei, Sancte Míchael, Réquiem, Decálogus, and for the dead *De profúndis* — Ps 129 with its versicles and the *Fidélium, Deus* collect — and the sequence *Dies iræ*); and the `LITANIES` registry (`LitanyKey`) — *Litaníæ Lauretánæ* (Loreto), *Litaníæ Sacratíssimi Cordis Iesu* (Sacred Heart), *Litaníæ Sanctíssimi Nóminis Iesu* (Holy Name), and *Litaníæ Humilitátis* (Humility — a private devotion, and the one litany whose Latin is ours rather than sourced), *Litaníæ Sancti Ioseph* (St. Joseph, incl. the seven invocations added in 2021), *Litaníæ Pretiosíssimi Sánguinis D.N.I.C.* (Precious Blood), and *Litaníæ Omnium Sanctórum* (All Saints, traditional form) — all six litanies approved for public recitation, plus Humility. **Every litany is `kind: "linear"`** and steps through sections with the bead strand (and is therefore persisted). The six one-text litanies are cut by **line range** — the `litany(name, nameTr, type, sections)` helper takes `[label, firstLine]` pairs and stamps each item with `lines: [start, end)`, which `sliceLines` applies to the Latin *and* every translation, since the translations keep the Latin's line structure (a test enforces equal line counts). Labels are each section's opening words or theme (Loreto: Kyrie → Sancta María → Virgo → Spéculum iustítiæ → Regína → Agnus Dei); the Kyrie and Trinity open every litany, and the Agnus Dei, versicle and collect close it. The Litany of the Saints instead builds **fifteen steps, one per section** (Supplicátio → eight saint groups → Ad Christum → Necessitátes → Conclúsio → Psalmus LXIX → Versículi → Collectæ, via `LITANY_SAINTS_SECTIONS` / `buildSaintsLitany`), and each of its sections is its own `LITANY_SAINTS_*` prayer type. At 225 lines per language it is by far the longest text in the app, and its **Czech is our own translation** (see below).
- `src/rosary/staticPages.ts` — **crawlable prayer pages**, generated at build time by the `staticPages` plugin in `vite.config.ts`: `buildStaticPages(base, siteUrl)` → `{ pages, sitemap }`. For every built-in prayer set (one *Rosárium* page for the rosary: its prayers and every mystery set's clauses), in every locale, `<locale>/<slug>/index.html` — the Latin beside the translation, straight from the registries — plus a `<locale>/` index; `slugify` folds the Latin name (`Litaníæ Lauretánæ` → `litaniae-lauretanae`). Each page carries canonical/hreflang/Open Graph tags and a *Pray it in the app* link, `<base>#pray=<key>`, which `Rosary` opens on mount (`isBuiltInKey` in `navigation.ts`; the fragment is cleared first). Its chrome strings (`PAGE_STRINGS`) and the notes on texts that are our own (`NOTES`, mirroring the banners in `prayers.ts`) live here, not in `i18n.ts`. Like the app, the Latin is never tagged `lang="la"`. The sitemap is written only with `SITE_URL` (it needs absolute URLs), and `robots.txt` only when the base is `/`; under a sub-path, submit the sitemap in Google Search Console. A new prayer set gets its pages automatically. Covered by `staticPages.test.ts`.
- `src/rosary/chaplet.ts` — the **Chaplet of Divine Mercy**'s start-screen switch: the `ruzenec_chaplet_full` preference (`loadSavedChapletFull` / `saveChapletFull`, off by default), `chapletKey(full)`, and `chapletToOpen(full, kept)` — a kept place in either form wins over the switch (the later of two), so flipping it never strands a half-prayed chaplet. Covered by `chaplet.test.ts`. The chaplet itself lives in `sequence.ts`: `buildChaplet(full)` and the `CHAPLETS` registry (`ChapletKey`: `misericordia` = the prescribed prayers, 63 steps; `misericordia-plena` = with the optional ones, 69). Two keys rather than one with a setting, so a saved step always belongs to the sequence it was counted in. It is `kind: "rosary"` (`isChapletKey` in `navigation.ts`) and reuses the rosary's `beadId`s — Pater Noster / Ave María / Credo on `tail-of` / `tail-hm-0` / `tail-hm-1`, `ring-of-${d}` for *Pater ætérne*, `ring-hm-${d}-${h}` for *Pro dolorósa* — so `RosaryBeads` draws it unchanged; the two tail beads it leaves unused (`tail-creed`, `tail-hm-2`) are drawn faint and never lit. In a decade the chip reads `III. Pro dolorósa`, and the tenth *Pro dolorósa* gets the decade-end double pulse. The static pages give it one page (`corona-divinae-misericordiae`, the full form, first decade only) in the rosary group. Never offered in plans (it would lose its ring).
- `src/rosary/plans.ts` — **user-defined prayer plans**: `Plan` / `PlanStep` / `PlanItemKey` / `PlanSetKey` types, the `ruzenec_plans` storage (own `PLANS_VERSION`, `loadPlans` / `savePlans`), `sanitizePlan` (validates anything claiming to be a plan — own-property step keys, clamped repeats, the `MAX_PLAN_STEPS` / `MAX_PLAN_LENGTH` / `MAX_PLAN_NAME` caps), `buildPlanSequence`, `planLength(steps)`, `PLAN_ITEM_GROUPS` (what the editor may offer), the share-link codec (`encodePlan` / `decodePlan` / `planShareUrl` / `readSharedPlanFromHash`, `LONG_SHARE_URL`), and the backup (`exportPlans` / `parsePlansBackup`). **Own prayers:** a plan may carry `custom: CustomPrayer[]` (`{ id, title, text, textTr? }` — the Latin text and an optional translation in the UI language), referenced by steps as `custom:<id>` (`isCustomKey` / `customKeyOf` / `findCustom` / `newCustomId` / `stepName`). `sanitizePlan` caps them (`MAX_CUSTOM_PRAYERS` / `MAX_CUSTOM_TITLE` / `MAX_CUSTOM_TEXT`), drops empty or unused ones and steps naming a missing one; the field is optional, so `PLANS_VERSION` did not change. `buildPlanSequence` turns one into a `PRAYER_TYPES.CUSTOM` item carrying its text on `SequenceItem.custom`. A plan may contain *Orationes utilissimæ*, litanies, the Leonine prayers and the prayers for the dead (`PLAN_DEVOTIONS`, the editor's "Aliæ preces" group); a multi-step entry inlines as its own steps. Never the rosary (it would lose its bead ring) or the St. Bridget and St. Joseph prayers (their unsectioned Pater/Ave/Glória sub-steps would each become a bead). Covered by `plans.test.ts`.
- `src/rosary/PlansScreen.tsx` — the prayer-plan screen: the saved-plan list (pray / edit / share / delete) and the editor (name, ordered steps with ×repeat and ↑↓×, the grouped prayer picker (Orationes utilissimæ / Litaníæ / Aliæ preces), and **+ Vlastní modlitba** opening `CustomPrayerForm` — title, *Text latinsky*, optional *Text česky*/English; a custom step gets ✎ to edit it, and removing its last step drops it). Under the list, the **backup** card: *Zálohovat plány* downloads a JSON file, *Načíst zálohu* reads one back through a hidden file input, adding its plans with fresh ids after an in-app confirm (`askConfirm`). The header's back button is an arrow only, like the prayer header's. Exports `PlanIcon`, reused by the start-screen tile. A plan with a saved place drops it when edited (`Rosary.setPlans`).
- `src/rosary/i18n.ts` — UI strings and language state: `SUPPORTED_LOCALES` (**cs/en only**), `Locale`, `DEFAULT_LOCALE`, the `STRINGS` table, and `detectLocale()` (first tag from `navigator.languages` that is supported or in `LOCALE_FALLBACKS` — Slovak → `cs` — else `DEFAULT_LOCALE`, `en`). Also owns **two** independent `localStorage` preferences: the UI locale (`ruzenec_locale`, via `loadSavedLocale` / `saveLocale`) and the prayer-body language (`ruzenec_prayer_language`, `latin`/`translation`, via `loadSavedShowTranslation` / `saveShowTranslation`) — the header's 🌐 La / Cz / En button (`LanguageToggle`). The locale drives **both** the chrome *and* which translation the prayer card shows, so `SUPPORTED_LOCALES` and `PRAYER_TRANSLATIONS` must stay in step: adding a locale here won't compile until a full prayer table exists in `prayers.ts`. The Latin itself is never localized.

Covered by `storage.test.ts`.

Days are compared as local calendar days. Covered by `liturgy.test.ts`.

- `src/rosary/RosaryBeads.tsx` — SVG bead ring + `beadStyle` helper, drawn for every `kind: "rosary"` set (the three mystery sets and the chaplet). A tail bead no sequence item names is drawn faint and never lit (the chaplet's `tail-creed` and `tail-hm-2`). Props: `currentStep`, `sequence`, `accentColor`, `onJump?`.
- `src/rosary/PrayerSections.tsx` — horizontal bead strand for `linear` prayer sets (the Leonine, St. Bridget, St. Joseph prayers and the prayers for the dead, every litany, and user plans; bead radii scale down once a long plan crowds the strand): one bead per step on a faint thread, no text labels — the current step's name shows in the label chip below it. Items carrying a `section` are drawn larger and are tappable to jump; unsectioned sub-steps are small and inert. Props: `sequence`, `currentStep`, `accentColor`, `onJump`, `locale`.
- `src/rosary/PrayerCard.tsx` — the tappable white card. `PrayerBody` (internal) renders Hail Mary with the highlighted mystery clause, a plan's own prayer (`PRAYER_TYPES.CUSTOM`: plain text from `SequenceItem.custom`, the translation when the language button asks for it and one exists), or any other prayer's body text. Litanies (any `LITANY_*` type, via `isLitanyType`/`renderLitany`) get a distinct layout: left-aligned (not centered), one invocation per line. The parsing lives in **`src/rosary/litany.ts`** (pure, tested in `prayers.test.ts`): `parseLitany` turns a section's text into blocks, and **two or more consecutive invocations with the same response become a `run`** — the response is shown **once**, in an accent-coloured, right-aligned, upright (not italic) *℟ ora pro nobis* band that is `position: sticky` (it stays at the top of the scroll area while its run scrolls past), and the lines carry only the invocation, minus the comma that led into the response. A lone invocation (the Agnus Dei, *Propítius esto*) keeps its response inline, styled like the band (accent colour, upright, semibold). A plural form counts as the same response as its singular (`PLURAL_OF`: *oráte*/*ora*, *orodujte*/*oroduj*) — the Litany of the Saints alternates them line by line — and a run mixing both is labelled *ora(te) pro nobis* / *oroduj(te) za nás*, so each saints' section gets one band. The response is found by matching a known phrase (`LITANY_RESPONSES` — *miserére nobis*, *líbera nos*, *have mercy on us*, …), **not** by splitting at the last comma: responses like *líbera nos, Iesu* carry a comma of their own. Two rules keep that matching honest, and both are load-bearing: a candidate must **end its line** bar a short vocative (`MAX_RESPONSE_TAIL`), or a collect containing the words would be italicized to its full stop; and among the candidates the **longest wins**, or *That thou wouldst spare us, we beseech thee, hear us.* would split at *spare us*. `℣`/`℟` versicles, the `Orémus`/`Modleme se`/`Let us pray` collect, `{r}…{/r}` rubric labels, and the opening acclamations (the Kyrie and the *audi nos* pair, matched by `LITANY_ACCLAMATION` — repeated whole, so never split) keep their normal styling.
- `src/rosary/litany.ts` — pure litany layout logic: `LITANY_RESPONSES`, `MAX_RESPONSE_TAIL`, `responseStart`, `LITANY_ACCLAMATION`, and `parseLitany(text)` → `LitanyBlock[]` (`blank` / `plain` / `single` / `run`). Rendered by `PrayerCard`'s `renderLitany`.
- `src/rosary/analytics.ts` — privacy-first usage analytics (GoatCounter): cookieless, no PII, no consent banner. `initAnalytics()` (called from `main.tsx`) loads the beacon only in production, only when `GOATCOUNTER_CODE` is set, and never under Do-Not-Track; `track(path)` records events (`pray/<set>` from `Rosary.startSet`). Live: the code is set (`latin-rosary`, dashboard at latin-rosary.goatcounter.com); set it to `""` to switch analytics off entirely. `analyticsConfigured` gates the About privacy note.
- `src/rosary/AboutDialog.tsx` — modal "About" panel (app name, a link to the static prayer pages (`<base><locale>/`, new tab, so an installed app isn't navigated away), build-time `__APP_VERSION__` + `__BUILD_DATE__` rendered as `v0.20.1 · sestaveno 31. října 2026` via `toLocaleDateString(locale)`, description, creator/contact), opened from the start screen; themed, localized, Escape/backdrop to close. Creator name + contact live in the `CREATOR` constant at the top of the file (contact line hidden when empty).
- `src/rosary/Flag.tsx` — inline SVG flags for the language picker, one per `Locale` (Czech, Union Jack), drawn to a uniform 24×16 viewBox. The `switch` is exhaustive over `Locale`, so a new locale fails to compile until its flag exists. Props: `locale`, `width?`, `height?`. Used by `MysteryMenu`.
- `src/rosary/MysteryMenu.tsx` — start screen: one button per mystery set, then the **Chaplet of Divine Mercy** — whose box also holds, under a rule, the *S nepovinnými modlitbami* switch (`OptionSwitch`, passed as `PrayerSetButton`'s `footer`: with a footer the box is a `div` holding the start button and the switch side by side, since a button can't contain another) and opens the form `chapletToOpen` picks — then under the "Other Latin prayers" heading two collapsible groups via the reusable `CollapsiblePrayers` component — **"Orationes utilissimæ"** (`ORDINARY_PRAYERS`) and **"Litaníæ"** (`LITANIES`) — followed by the linear-set buttons (Leonine, St. Bridget, St. Joseph, the prayers for the dead) and the **prayer-plans tile**. Above everything, when a place is kept, a **"Rozepsaná modlitba" tile** (`continueWith`, from `Rosary`) offers the most recently prayed unfinished set: `Rosary` moves a set to the end of the `progress` map whenever its step changes (delete, then re-add — key order survives JSON and `resolveSession`), so the last key is the latest. From `liturgy.ts` it tags **today's mysteries** with a *dnes* / *today* pill and the **Marian antiphon in season** with *nyní* / *now*, and in November tags the prayers for the dead (Réquiem, De profúndis, Dies iræ, and the *Preces pro defunctis* button) with *nyní* too (`seasonBadges`, from `monthOfTheDead`), and in Eastertide notes under the Angelus that the Regína Cæli replaces it; the pills come from the `Badge` helper, the extra line from `CollapsiblePrayers`' `notes` (`onOpenPlans`, with the plan count as its subtitle); also hosts the language picker and theme toggle. Every row and both group headers are two-line: the **Latin name** with its **`nameTr[locale]` beneath it in `--text-muted`**, the shape the plans tile established. Aria labels use the localized name. Calls `onStart(key)`.

- `vite.config.ts` — reads `BASE_PATH`, configures React plugin, defines `__APP_VERSION__` (from `package.json`) and `__BUILD_DATE__` (ISO timestamp of the build; in `npm run dev` it's the dev-server start time), stamps the SW cache version at build time, emits the static prayer pages and sitemap (`staticPages`, see `src/rosary/staticPages.ts` — which is why `tsconfig.node.json` has the `DOM` lib: the app modules it imports reference browser types), and fills `%APP_URL%` in `index.html` with `SITE_URL` (the origin, from `.env`) + `BASE_PATH` — link previews need an absolute image URL; without `SITE_URL` the tags get the bare path.
- `CHANGELOG.md` — Keep a Changelog format.

## Domain model (in `src/rosary/`)

- `MYSTERIES` — three traditional mystery sets (`radostny` / `bolestny` / `slavny`), each with a display name, accent color, and 5 mystery clauses. (`prayers.ts`)
- `PRAYER_TYPES` — enum of prayer kinds. The rosary core is `SIGN_OF_CROSS`, `CREED`, `OUR_FATHER`, `HAIL_MARY`, `GLORY_BE`, `FATIMA`, `SALVE_REGINA`; the rest of the ~65 members cover the chaplet (`CHAPLET_*`), the Leonine, St. Bridget and St. Joseph (`IOSEPH_*`) prayers, the *Orationes utilissimæ*, and the litanies (`LITANY_*`, with one type per section for the Litany of the Saints). (`prayers.ts`)
- `buildRosarySequence(mysterySet)` — builds the linear 74-step prayer sequence: (`sequence.ts`)
  - Opening: Sign of Cross + Credo + Pater Noster + 3 Hail Marys (with the fixed `fidem` / `spem` / `caritátem` mystery clauses) + Gloria Patri (positions 0–6).
  - 5 decades, each: Pater Noster + 10 Ave Maria + Gloria Patri + Fatima (`O mi Jesu`) = 13 steps.
  - Closing: Salve Regina + Sign of Cross.
- `PRAYERS` — full Latin prayer texts as single-paragraph strings (Salve Regina is the only one with real line breaks for its three sections). (`prayers.ts`)
- `getHailMary(mystery)` — splits an Ave Maria into `before` / `mystery` / `after` so the per-decade mystery clause can be visually highlighted in the accent color. (`prayers.ts`)

## Sequence-bead mapping (beadId-driven)

`buildRosarySequence` stamps every prayer that has a bead with a stable `beadId`:

- Tail: `tail-creed`, `tail-of`, `tail-hm-0`, `tail-hm-1`, `tail-hm-2`.
- Ring: `ring-of-${d}` (Pater Noster for decade `d` ∈ 0..4) and `ring-hm-${d}-${h}` (Hail Mary `h` ∈ 0..9).
- Sign of Cross, Gloria Patri, Fatima, and Salve Regina deliberately have **no `beadId`** — the cross glyph at the tail tip, and the junction where the tail meets the ring, stand in for them.

`RosaryBeads` builds a `beadId → seqIdx` map from the live sequence on every render and uses that for every lookup. There are no magic indices anywhere — adding or removing prayers from the sequence won't desync the beads as long as new bead-bearing items carry a `beadId` matching the layout. Ring layout still assumes 5 decades of 1 Pater Noster + 10 Hail Marys; the first ring Pater Noster sits exactly at the junction (`angle = π/2`) and decades are separated by a single uniform gap.

The Chaplet of Divine Mercy (`buildChaplet`) reuses this mapping with its own items on the same beads; see `chaplet.ts` above.

If you change sequence structure, bump `STATE_VERSION` so saved progress doesn't desync.

### Decade jump

Pater Noster beads (tail + 5 ring beads) carry a transparent 11–12px hit circle that calls `onJump(seqIdx)` → `jumpTo(idx)` on the parent component. Hail Mary beads are deliberately not jumpable to avoid stray taps during swipes.

## Persistence

- `localStorage` key `ruzenec_state`, schema `{ version, active, progress }`. `progress` maps every **unfinished** multi-step set to its saved step, so leaving one set to pray another never loses a place; `active` is the set on screen when the app closed, reopened on launch. Keys are plain strings; `storage.ts` does only version/shape checks, and `navigation.resolveSession(loadSavedState())` validates every key against the registries (own-property check) and drops step 0, negative, and out-of-range steps.
- **Lifecycle of a place:** the back arrow `←` returns to the menu and *keeps* it (no prompt); the menu shows "Pokračovat · 23/74" under the set (the collapsible group holding it starts open); opening the set resumes there. **Finish** (last step) forgets it, and the header's ↺ button (shown past step 0, with a confirm) goes back to step 0, which also forgets it. Editing or deleting a plan drops that plan's place (`Rosary.setPlans`), since its steps changed.
- **Only multi-step sets persist**: the rosary, both forms of the chaplet, the linear devotions (Leonine, St. Bridget, St. Joseph, the prayers for the dead), every litany (all `kind: "linear"`), and a user plan that still exists — gated by `isPersistableKey`. Single-prayer sets (the ordinary prayers) have no progress to resume and stay session-only.
- **User plans live under their own key**, `ruzenec_plans`, with their own `PLANS_VERSION` — deliberately *not* inside `ruzenec_state`, which is discarded on every `STATE_VERSION` bump and cleared on reset. That is right for a position but would silently destroy user data. `sanitizePlan` re-validates every plan on load, so a renamed registry key degrades a plan instead of crashing the app. `STATE_VERSION` was **not** bumped for this feature: no existing sequence changed, and a bump would needlessly discard an in-progress rosary on update.
- `STATE_VERSION` (currently 6) — increment on any structural change to the sequence **or this schema**; `loadSavedState` discards mismatched versions silently. Versions 4 (a single `{ selectedSet, currentStep }`) and 5 (today's shape) are **migrated** instead: version 6 only lengthened the sequences of plans that contain a litany, so the migration drops places kept in plans (`plan:*`) and carries every other place over. On the next sequence change, decide again what still lines up — don't just extend the migration.
- State is saved on every `currentStep` / `selectedSet` / `started` / `progress` change; the key is removed once nothing is open and no place is kept.
- Five standalone UI preferences persist under their own keys, independent of the session and not versioned: `ruzenec_chaplet_full` (see `chaplet.ts`; the chaplet's optional-prayers switch), `ruzenec_locale` (see `i18n.ts`), `ruzenec_prayer_language` (see `i18n.ts`; `latin`/`translation` — the header's language button; it stores *which side*, not which language, so it survives a locale change and defaults to Latin), `ruzenec_font_size` (see `fontSize.ts`; a numeric step index), and `ruzenec_theme` (see `theme.ts`; `light`/`dark`, defaults to the OS setting until chosen). All survive reset and reload.

## Interactions

- **Tap** prayer card → next.
- **Swipe** right → previous; left → next (≥50px, <600ms, mostly horizontal).
- **Keyboard** `→` / `Space` / `Enter` → next; `←` → previous (ignored when focus is in an input).
- **Tap a Pater Noster bead** on the SVG → `jumpTo(seqIdx)`. Implemented as a transparent hit-circle behind each PN; HM beads are not jumpable.
- **Haptic** `navigator.vibrate(25)` on every step (including jumps), and a double pulse (`[35, 90, 35]`) on reaching a decade's Gloria Patri (in the chaplet, its tenth *Pro dolorósa*), so the end of a decade can be felt without looking.
- **Dialogs** are in-app, never `window.confirm`/`alert`/`prompt`: `askConfirm({ message, detail?, confirmLabel, cancelLabel | null, color })` in `ConfirmDialog.tsx` mounts its own root and resolves a promise (restart, plan delete, shared-plan and backup import, the share-link fallback). While one is open it owns the keyboard — its capturing listener stops every key but Tab, and `Rosary`'s key handler also bails while a `[role="alertdialog"]` exists (the dialog's effect runs only after it renders).
- **Landscape** (`(orientation: landscape) and (min-width: 640px)`, `WIDE_LAYOUT` / `useMediaQuery` in `Rosary`): the progress (ring or strand) and label get a column on the left and the card sits beside them, vertically centred; the ring may grow (`RosaryBeads` `maxHeight`/`maxWidth` props).
- **Decade label:** within a rosary decade the label chip names the decade and quotes its mystery clause in full, following the prayer-language switch: Latin `II. quem, Virgo, …` (just the Roman numeral, as Latin prayer books head the mysteries; chip tagged `lang="la"` — safe, the chip is Arial) or the translation via `t.decadeLabel` (`2. desátek: s kterým jsi, Panno, …`) from `MysterySet.mysteries` / `mysteriesTr`. It may wrap to two lines. Every decade item — Pater Noster, Ave Marías, Gloria, Fatima — carries `decade`. The chaplet's decades have no mystery: its chip reads `III. Pro dolorósa` (the Roman numeral and the item's Latin label, in either language).
- **Wake Lock API** keeps the screen on while any prayer is open (re-acquired on `visibilitychange`).
- Active bead glows in the mystery's accent color; the cross icon glows when a Sign of Cross step is active.
- **Prayer plans** — the start-screen tile opens `PlansScreen`: build a named plan from the ordinary prayers, litanies, the Leonine prayers and prayers of your own (with a ×repeat per entry), then pray it as a `linear` set with the bead strand. Share hands out a `#plan=…` link (native share sheet → clipboard → prompt), with a warning toast past `LONG_SHARE_URL` since own prayers travel in it. Plans live only in this browser; the backup card saves and restores them as a file.
- **Opening a prayer from a link** — `<base>#pray=<key>` (the static pages' button) opens that built-in set on launch, resuming a kept place like a menu tap. `Rosary` clears the fragment first, so a reload or the back button doesn't reopen it, and ignores any key `isBuiltInKey` rejects (a plan key, an unknown or prototype name). It goes through `startSet`, so it is counted in analytics like any other start.
- The header back button (an arrow-only `←`, labelled for screen readers) returns to the menu without a prompt — the set's place is kept (see Persistence). The ↺ button beside it restarts the set after a confirm. Header buttons are 40px tall (≥44px wide) — touch-sized.
- The **language toggle** (`LanguageToggle`, the far-right button of the header's control row) is a **switch** (`role="switch"`): one button showing both sides as segments, `La | Cz` (`La | En` — `t.prayerLanguageShort`), the active one filled white; one tap flips it. The choice persists in `ruzenec_prayer_language` and is independent of the UI locale.
- The header's right side holds the **text-size control** (`FontSizeControl`): a compact "Aa" button opening a smaller-A / bigger-A nudge popover that steps the prayer body through a bounded scale (`fontSizeClamp`) and persists the choice. Only the prayer-body text scales — UI chrome stays fixed.

## Theming (light / dark)

- Neutral colors are **CSS custom properties** defined in `src/index.css`: a light set on `:root` and a dark override on `:root[data-theme="dark"]` (`--bg`, `--surface`, `--surface-hover`, `--border`, `--border-strong`, `--text`, `--text-strong`, `--text-soft`, `--text-muted`, `--bead-past`, `--bead-future`, `--thread`, `--track`, `--nav-fade`, `--rubric`). Inline styles reference them as `var(--…)`.
- **Red rubrics:** wrap text in a prayer body with `{r}…{/r}` to render it in the missal-style red `--rubric` color (e.g. the seasonal labels in Alma Redemptóris). `PrayerCard`'s `withRubrics` parses the markup; the markers never reach the screen.
- **Don't hardcode neutral colors** in components — add/extend a token. Mystery **accent** colors stay raw (passed via JS), used for solid fills (header, active bead, buttons, progress); for accent-as-*text* on the dark card (highlighted clause, label chip) run it through `accentText(accent, theme)` so dark accents stay legible.
- **SVG caveat:** `var(--…)` does **not** resolve in SVG presentation *attributes* (`fill="…"`, `stroke="…"`). Set them via the `style` object instead (see `RosaryBeads.tsx` / `PrayerSections.tsx`).
- `theme.ts` toggles `data-theme` on `<html>`; an inline script in `index.html` sets it before first paint (anti-FOUC) from `ruzenec_theme` or the OS. `Rosary` holds the state and follows OS changes until the user picks explicitly. The sun/moon toggle lives top-left on the start screen (`MysteryMenu`), mirroring the language picker, and again in the prayer header's control row (first on the right); both draw the shared `ThemeIcon` glyph.

## Typography

- Prayer body uses **EB Garamond** (Adobe Garamond Pro lookalike), **bundled** from the `@fontsource/eb-garamond` package (imported in `main.tsx`: 400, 400 italic, 500, 600), not loaded from Google Fonts. Same-origin font files are cached by the service worker, so the font works offline (Google's stylesheet was a no-cors request the SW could not cache), and no visitor's IP reaches a third party. Each CSS file declares every subset with its `unicode-range`, so only the subsets in use (Latin, Latin Extended for Czech) are downloaded; don't switch to the per-subset `latin-*.css` files — they lack `unicode-range` and override each other. `main.tsx` calls `document.fonts.load(…, "ǽ")` for each imported face at startup: on Latin screens ǽ (U+01FD) is often the only Latin Extended glyph, so that subset would otherwise be fetched only when it first appears and, if that fetch failed (offline), stay in a system serif. Keep this in step with the imported faces.
- The prayer body is **deliberately NOT tagged `lang="la"`**. EB Garamond's Latin `locl` forms render **u→v** (Roman style) under `lang="la"`, and `font-feature-settings: "locl" 0` does **not** reliably suppress a language-triggered feature on mobile (Safari ignores it). So Latin is left untagged (`Iesus`, not `Iesvs`); only the *translation* gets a `lang` tag (the UI locale) — see `bodyLang` in `PrayerCard.tsx`. **Do not add `lang="la"` to prayer-text containers.**
- All UI chrome (buttons, headings, counters) stays in Arial.
- Prayer texts are deliberately collapsed to single paragraphs — the browser handles wrapping. Salve Regina is the exception: it preserves its three sections (main / versicle+response / Orémus).

## Conventions

- **Keep `README.md`, `CLAUDE.md` and `CHANGELOG.md` in step with every change, in the same PR.** A new prayer or feature goes into README's feature list (and its Sources line if the text is ours); in CLAUDE.md, besides the file's own entry, check every place that enumerates the affected thing (file map entries of the components it touches, Persistence, Interactions, the test descriptions, Conventions, the list of texts that are our own). A user-visible change gets a CHANGELOG entry under `[Unreleased]`.
- Don't introduce a CSS framework or a state library — the app's simplicity is intentional. (TypeScript is fine — it lives in `src/rosary/*.ts` for data/types and `*.tsx` for components, with strict mode on.)
- New prayer types or sequence changes: update `PRAYER_TYPES`, `PRAYERS` **and every translation table** in `src/rosary/prayers.ts` (extend `StaticPrayerType` if the new prayer has static text), the builder in `src/rosary/sequence.ts` (stamp new bead-bearing items with a `beadId` matching the layout), the bead layout in `src/rosary/RosaryBeads.tsx` if structure changes, and bump `STATE_VERSION` in `src/rosary/storage.ts`.
- To add an **ordinary (single) prayer** or a **litany**: add its text to `PRAYERS` **and to every table in `PRAYER_TRANSLATIONS`** (`PRAYERS_CS`, `PRAYERS_EN` — as a new `StaticPrayerType`; the `Record` types make a missing one a compile error), then add an entry to `ORDINARY_PRAYERS` (whose `build()` returns the one-step sequence) or to `LITANIES` (extending `LitanyKey`, via the `litany(…)` helper with its section cuts as `[label, firstLine]` — keep every translation line-for-line with the Latin), with a `nameTr` for every locale. If its response phrase is new, add it to `LITANY_RESPONSES` in `litany.ts` in each language. It appears automatically as a link in the matching start-screen group, and gets its own static page in every locale (`staticPages.ts`) ("Orationes utilissimæ" / "Litaníæ") — no `MysteryMenu`/`Rosary` changes needed. A litany whose sections differ too much to share one text can instead give each section its own `StaticPrayerType` and a custom `build()`; see the Litany of the Saints and `LITANY_SAINTS_SECTIONS`. Seasonal/labelled sections use `{r}…{/r}` red rubrics (see Theming). A new ordinary prayer or litany is offered in the plan editor automatically — `PLAN_ITEM_GROUPS` is derived from the two registries.
- **User prayer plans** are user data, not a registry: they're loaded from `ruzenec_plans` and passed *down* into `getPrayerSetMeta` / `buildSequence` / `isPersistableKey` / `resolveSession`, which keeps `navigation.ts` free of storage. A plan key is `plan:<id>`, so it can never collide with a registry key. Two limits are enforced in **both** `sanitizePlan` and the editor (`fits`) — a plan that only the editor allowed would be silently dropped on the next load. Don't let a plan contain the rosary or the St. Bridget prayers: the rosary would lose its bead ring, and St. Bridget's sub-steps would each become a bead. A linear devotion whose every step is a section (the Leonine prayers) inlines cleanly and may be added to `PLAN_DEVOTIONS`.
- **Static prayer pages** (`staticPages.ts`) are plain HTML strings built from the registries, with no React and no client script beyond the theme: keep them that way, so they stay fast and crawlable. Everything interpolated goes through `escape`, and their few chrome strings live in `PAGE_STRINGS`, which must cover every locale. A new prayer text that is our own gets a note in `NOTES` as well as the banner in `prayers.ts`. Don't change a page's slug lightly: it is the URL search engines have indexed (the slug comes from the Latin `name`, so renaming a prayer moves its page).
- **Sharing a plan** goes through the URL fragment (`#plan=<name>;<key>*<n>,…[;<id>:<title>:<text>[:<textTr>],…]` — the optional third part carries its own prayers, every field `encodeURIComponent`-escaped), never a server. An own prayer is always rendered as plain text, never markup, so a shared link can't inject anything. `Rosary` imports it once on mount: fragment cleared first, an in-app confirm (`askConfirm`) for consent, fresh id assigned so a shared plan can't overwrite a local one.
- Keep accessibility attributes when editing UI: `aria-label` on interactive buttons, `aria-live="polite"` on the prayer card, `aria-hidden="true"` on decorative SVGs. (Do **not** add `lang="la"` to prayer text — it triggers EB Garamond's u→v; see Typography.)
- Latin diacritics (acute accents, æ, œ) are part of the prayer text — preserve them exactly when editing.
- Every prayer text is transcribed from a trustworthy source **except** the St. Bridget `BRIGIT_*` entries, which are our own translation (no authoritative Latin original exists for that devotion), the **Czech** Holy Name litany, whose invocations are sourced but whose closing collect is our own wording, the **Latin** Litany of Humility, which has no authoritative original to transcribe (modern devotion, author unknown, published in 1880 as a translation from the French) — its pointing is ours, assembled from two Latin witnesses; the **Latin** of the Chaplet of Divine Mercy's optional prayers (`CHAPLET_OPENING`, `CHAPLET_BLOOD_WATER`, `CHAPLET_CLOSING` — the Diary is Polish and the Latin in circulation is unofficial and inconsistent; the core chaplet prayers are the Latin in common use), the **Czech and English headings** of St. Joseph's seven sorrows and joys (the only Czech text in circulation, FATYM / farnost Čáslav, is a modern paraphrase, not the Latin), the **English** *Dies iræ* (our literal line-for-line rendering: Irons' English exists only in altered hymnal versions; the Czech is Schaller's, split into lines by its rhymes), and the **Czech** Litany of the Saints, which is our translation of the traditional Latin, because the Czech liturgical books carry only the modern short form (Kancionál 068A/B). All are flagged with banner comments in `prayers.ts`. They're flagged with a banner comment in `prayers.ts`; if a sourced Latin booklet is ever obtained, replace those texts verbatim. Don't add further unsourced prayers without flagging them the same way. `PRAYERS_EN` was written from the received traditional English and then checked text by text against online witnesses (vatican.va, EWTN, the Liturgy of the Hours, …); the banner above it records which witness each text follows and where the Latin was preferred over it.
- The icon (`public/icon.svg`) is hand-tuned to mirror the rosary visualization in the app; if you change the in-app SVG, consider keeping the icon in sync — and re-render the PNG icons (and `og-image.png`) whenever `icon.svg` changes.
